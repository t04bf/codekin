# 简历证件照直传接口

后端开放上传签名与文件确认。前端已接入上传流程，按用户确认的范围，编辑页继续使用本地图片预览，简历保存及私有图片展示接口尚未接入。

## 接口与用途

沿用文件服务通用接口，通过新增共享用途枚举 `UploadType.RESUME_PHOTO` 区分证件照与用户头像，不复制一套签名算法或上传接口。

| 接口 | 行为 |
| --- | --- |
| `GET /api/files/upload-types` | 登录后读取用途、允许扩展名/MIME、字节数、尺寸和总像素限制，新增 `RESUME_PHOTO` |
| `POST /api/files/upload/signature` | 当前登录用户申请 S3 POST Policy；用户身份来自网关验签上下文 |
| `POST /api/files/{fileId}/complete` | 当前用户确认本人上传，校验实际图片并生成独立正式文件；返回 `fileId`、用途、实际大小与 MIME |

仍使用 Bearer 登录态和统一 `R<T>` 响应，HTTP 200 的 `code = "0"` 表示业务成功。文件正文使用浏览器直传对象存储，响应按 S3 协议处理。

签名请求：

```json
{
  "typeCode": "RESUME_PHOTO",
  "fileName": "portrait.png",
  "size": 123456,
  "contentType": "image/png"
}
```

返回 `data` 包含字符串 `fileId`、`uploadUrl`、`method = "POST"`、SDK 签发的 `fields`、`expiresAt` 与 `confirmationExpiresAt`。FormData 先按返回值添加所有 `fields`，最后添加名为 `file` 的图片，不给存储请求附带应用 JWT，不手写 multipart boundary。完成直传后，以 `fileId` 调用确认接口。

## 文件策略

| 项目 | 简历证件照策略 |
| --- | --- |
| 源文件 | JPEG/JPG、PNG、WebP，1 字节至 5 MiB（5,242,880 字节） |
| 源图尺寸 | 单边最多 4096 像素，总像素最多 12,000,000 |
| 正式图片 | 静态 PNG，最长边最多 1024 像素，保持比例，不裁剪、不放大 |
| 元数据与动画 | 共用现有图像重编码策略，移除源元数据；拒绝动画 WebP |
| 默认签名/确认有效期 | 5 分钟 / 15 分钟，由原 Nacos 配置控制 |
| 默认限流 | 每用户每用途 10 分钟最多 10 次，与 `AVATAR` 分开计数 |
| 临时目录 | `uploads/resume_photo/{userId}/{随机UUID}.{源扩展名}` |
| 正式目录 | `files/resume_photo/{userId}/{fileId}.png` |

1024 是本项目的输出预算选择，并非证件照或打印行业标准。复用 SDK POST Policy 对临时 key、MIME 与最大文件大小的限制，确认时再核验真实格式、实际字节数和像素。正式对象与签名可覆盖的临时对象分离，沿用已有过期临时对象清理。

## 业务边界与兼容

- `file_object.type_code` 已为 `VARCHAR(32)`，现有索引适用，无需新增表或数据迁移。
- `/api/files/**` 已由网关路由至文件服务，无需新增公开路径或 Nacos 上传白名单。
- `getReadyFile(fileId, ownerUserId, RESUME_PHOTO)` 的现有 Dubbo 契约可核验归属、用途和 READY 状态；新增枚举不会改变返回结构或 RPC 版本。
- 证件照仍位于私有存储桶，`getAvatarUrls` 保持 `AVATAR` 过滤，不将证件照纳入公开头像访问；HTTP 确认响应不提供内部路径或访问链接。
- 后续保存简历时应引用经确认的文件 ID，通过文件服务核验，并在本人查看/导出时获取受控读取链接；不要持久化短期签名 URL，也不要把证件照绑定到用户头像。
- 本阶段没有启动服务、执行数据库脚本、修改运行中的 Nacos 或对象存储，也没有声称完成真实浏览器直传联调。

- 另有 14 项兼容测试通过：13 项原头像业务回归及 1 项 Dubbo 回环网络/Fastjson2 契约测试；后者实际调用新增 `RESUME_PHOTO` 用途。合计 45 项测试通过，文件与用户模块及其依赖编译通过。
- 使用项目现有 JDK 26 构建；数据库、Redis 和对象存储使用隔离替身，SDK 签名及真实 ImageIO 解码在本地执行。

## 前端上传接入

复用 React 头像的 `fileApi`、鉴权请求与独立存储请求实例，通过 TanStack Query 查询 `RESUME_PHOTO` 限制并管理上传状态。选择图片后申请签名，直接传原始 `File`（签名声明的 MIME/字节数与正文一致），随后调用确认；客户端另生成最长边 1024 的本地预览，仅在确认结果的文件 ID 和用途均一致后替换原照片。

上传期间显示阶段/百分比，限制重复提交和关闭/替换照片；失败保留原照片，可以再次选择同一文件重试。匿名用户可编辑草稿，上传按钮显示登录提示；上传中切换账号后不再确认或写入新账号草稿，切换简历时不更新另一份简历。

按用户要求，本次没有新增读取接口，也没有实现简历保存或远程文件关联；既有 IndexedDB 本地预览继续生效，不存签名链接。确认产生的正式文件尚未与简历持久化关联，沿用既有正式文件暂不回收规则；以后接入简历保存时需补齐文件引用及私有读取流程。

57 项前端测试与生产构建通过，其中 7 项新增测试验证流程顺序、原始文件、服务端限制、失败/确认异常、重试、重复提交、账号变更及挂载编辑面板保留原照片。内置浏览器在独立 MSW 环境真实选择项目 PNG，发送 multipart/FormData 并确认成功，验证本地照片显示、空链接输入框不误清照片、关闭和再次打开。模拟存储拒绝携带应用 JWT、MIME/大小不符、字段缺失或 file 不在最后的请求；这属于前端契约验证，不等同于真实 SeaweedFS 联调。

## 真实存储 CORS 修复（2026-10-05）

React 前端运行在 `5174`，原存储桶只允许 `5173`。头像和证件照共用直传存储，实际 POST 虽返回 204，浏览器因缺少对应的 `Access-Control-Allow-Origin` 拒绝读取响应，两种用途均无法继续确认。SeaweedFS 的 OPTIONS 预检返回通配头，因此预检成功不足以发现此问题。

已在 Nacos 仓库副本、`.env.example` 和本地后端 `.env` 中补充 `127.0.0.1:5174`、`localhost:5174`，保留原 `5173` 来源；`deploy/.env` 是后端 `.env` 的符号链接。仅更新运行中 Nacos 的 `codekin-file.yml` 对应来源配置，保留其余内容；通过现有 MinIO Java SDK 更新真实桶的 `codekin-web-upload` 规则并保留其他规则，无需重启服务即可生效。

使用真实 SeaweedFS 和 SDK POST Policy 上传项目示例 PNG（106908 字节），三个来源 `http://127.0.0.1:5174`、`http://localhost:5174`、`http://127.0.0.1:5173` 均返回 204 和匹配来源的响应头；HEAD 验证对象大小后已删除临时测试对象。非白名单来源仍没有跨域许可，匿名请求仍为 403。此次验证覆盖真实签名直传及 CORS，不包含登录用户的业务确认、头像资料保存或简历保存。
