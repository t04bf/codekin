# RPC 统一返回与异常处理

日期：2026-10-04。

## 返回结构

全局 `org.ninestick.codekin.model.common.RpcResult<T>` 位于 `codekin_model`，使用普通 class、Lombok Getter/Setter/Builder、无参构造及 Serializable，兼容 Dubbo 的 Fastjson2 传输。

| 字段 | 语义 |
| --- | --- |
| code | 成功为公共 SUCCESS 的 `0`；失败沿用业务 Recode 或公共 RpcCode |
| message | 成功说明或错误说明，支持 SLF4J 的 `{}` 占位符 |
| data | 成功业务数据；失败不返回部分业务数据 |

无返回数据的 RPC 方法也要声明为 `RpcResult<Void>` 并返回 `RpcResult.success(null)`。`isSuccess()` 是根据 code 判断的辅助方法，不能仅根据 data 是否为空判断成功。

```java
RpcResult.success(file);
RpcResult.failure(CommonCode.NOT_FOUND, "文件 {} 不存在", fileId);
```

## 公共异常出口

`codekin_common/codekin_dubbo` 为公共运行时模块，统一引入已由根 POM 管理版本的 Dubbo Starter，并通过 SPI 自动激活过滤器，不需要在每个 RPC 方法中重复 try/catch。

- 提供方：BusinessException 保留业务码和已格式化消息；参数异常返回公共参数错误码；未知 Exception 返回 `RPC_INTERNAL_ERROR` 及安全说明/异常类型。
- 消费方：集群调用外层转换最终的同步或异步调用失败，包括超时、网络失败和无可用实例，返回 `RPC_CALL_FAILED`。不在单次节点调用里提前吞异常，保留框架的重试判断；这不意味着超时后服务端未执行成功，写操作仍要设计幂等。
- null、缺少 code 或非 RpcResult 的响应返回 `RPC_INVALID_RESPONSE`。
- 原始异常消息可能含 SQL、请求 URL 或密钥，因此未知异常不原样放入 message，也不在本组件日志中打印请求参数。业务自定义消息应由业务方保证不含敏感内容。
- 服务启动、代理初始化或序列化结果在过滤器之外失败时，仍可能发生框架异常，应用边界需要兜底；提供方无法为根本没到达它的请求生成结果。
- JVM 致命 Error 不转换成可重试业务失败。Dubbo 自身的元数据、echo 等框架方法保留原协议。

异常转换同时处理返回响应中的异常及 Future 的异常完成，不在异步操作刚返回时抢读未完成的结果。不重复套结果，保留响应 attachments。

## 已迁移接口

```java
RpcResult<ReadyFileDto> getReadyFile(String fileId, Long ownerUserId, String typeCode);
RpcResult<Map<String, String>> getAvatarUrls(List<String> objectKeys);
```

文件不存在、未确认或不属于指定用户，返回公共 NOT_FOUND 结果；不泄露其他用户是否存在该文件。用户服务先检查结果码和归属，再保存头像；RPC 失败结果即使错误地附带 data，也不会用于修改用户资料。获取展示 URL 失败时继续使用默认头像。

这是不兼容的返回结构变更。`FileRpcConstants.VERSION` 从 `1.0` 调整为 `2.0`，提供方和消费方共用常量，避免旧 DTO 契约与新结果契约混用。需要文件服务和用户服务使用更新后的代码重启，本次没有修改运行中的服务、容器或数据库。HTTP 接口仍使用原有 `R<T>`。

## 新服务接入约定

1. 业务服务依赖 `codekin_dubbo`，RPC 契约依赖 `codekin_dubbo_api`。
2. 接口所有业务方法声明 `RpcResult<T>`，共享数据类型放在 `codekin_model`。
3. 成功显式构造结果；业务失败可返回 failure，也可抛公共 BusinessException，由过滤器处理。
4. 消费方首先检查 isSuccess，再按所属业务的错误语义处理，不直接调用失败结果的 data。

## 实现依据

使用 [Dubbo Filter 与 ClusterFilter 扩展机制](https://dubbo.apache.org/en/overview/mannual/java-sdk/reference-manual/architecture/service-invocation/)，提供方和消费方分别处理所属调用边界。网络与回调行为以仓库实际使用的 Dubbo 3.3.6 进行测试。

## 验证结果

- Java 26 下整个后端 Maven 编译通过。
- 本次定向测试共 23 项通过，失败、错误、跳过均为 0。
- 覆盖同步和异步异常、业务错误码及参数化消息、非法响应、敏感原始消息隔离，以及消费方失败结果不得用于更新头像。
- 实际 Dubbo TCP 调用验证 Fastjson2 能正确还原泛型 DTO/Map、业务和未知异常能返回统一结果、网络调用超时能返回 `RPC_CALL_FAILED`。

验证未依赖正在运行的 Nacos、数据库或对象存储，也未更新它们的配置。

## Dubbo 注册期间的 JSON 初始化

文件服务启动日志中的 `NoClassDefFoundError: com/alibaba/fastjson/JSONException` 出现在 `JsonUtils.loadExtensions` 和注册报告生成路径。Dubbo 3.3.6 的合并 JAR 列出了多个可选 JSON 实现；默认扫描时，ServiceLoader 在检查缺依赖的旧 Fastjson 实现构造器阶段就抛出了错误。这与 RPC 接口执行异常不同，会直接中断服务启动。

公共模块通过 Boot 4 的 `EnvironmentPostProcessor` 在配置加载和服务注册之前，将 Dubbo 原生 JVM 属性 `dubbo.json-framework.prefer` 默认设置为 `fastjson2`。引用 `codekin_dubbo` 的服务自动启用，显式 JVM 属性仍保留。Dubbo 自带的 Fastjson2 实现位于扩展列表首位，指定后会直接选择它，无需加载后续缺依赖的可选实现。

`dubbo.protocol.serialization=fastjson2` 只指定 RPC 传输序列化，不能代替内部注册报告的 JSON 实现选择；此初始化设置也不作为可动态刷新的 Nacos 配置。

独立 JVM 回归测试排除了旧 Fastjson、Gson、Jackson 2，确认未配置时复现相同缺类错误，经过真实 Boot 自动装配后 JSON 编解码成功，并验证显式 JVM 属性不会被覆盖。新增测试与原有结果过滤器测试共 10 项通过。没有为绕过该错误引入 Fastjson 1 依赖。

参考 [Dubbo 3.3.6 的 JsonUtils 实现](https://github.com/apache/dubbo/blob/dubbo-3.3.6/dubbo-common/src/main/java/org/apache/dubbo/common/utils/JsonUtils.java)。本次验证没有连接正在运行的 Nacos，实际服务注册需以重新启动后的日志确认。
