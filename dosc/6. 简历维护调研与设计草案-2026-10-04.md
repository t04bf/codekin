## 1. 当前基础与参考项目结论

Codekin 已有 Vue 3 / Pinia / Element Plus 前端，Spring 用户服务、文件服务、网关身份上下文、MyBatis-Plus、MySQL、Redis、Dubbo 和私有对象存储。现有 deploy.sql 包含 user_auth、user_profile、file_object，尚无简历表。简历不能直接塞进 user_profile；同一用户可维护针对不同岗位的多份独立简历。

## 2. 业务范围建议

首期完整闭环：简历列表 → 选择模板/空白创建 → 编辑标准模块与自定义内容 → 实时预览 → 自动/手动保存 → 重开恢复 → 切换模板 → 复制/删除 → PDF 导出。

建议先实现两个差异明确的模板（单栏、双栏），所有模板均支持自定义字段和模块；不要先铺开九个模板再发现分页和字段不兼容。模板数量是建议，不是已确认需求。AI 优化、任意 PDF 导入、分享链接、团队协作、模板可视化设计器、Word 导出不默认包含在本期。

## 3. 数据表建议

采用关系型元数据列 + JSON 文档。理由是读取和保存的业务单位是整份简历，自定义结构、排序与模板切换频繁；为每个教育经历字段或自定义值建表会显著增加同步复杂度。代价是正文跨用户筛选、统计不方便；将来确有检索需求再建立可重建的检索投影，不能现在把正文拆成无限通用 EAV 表。

MySQL JSON 会检查合法 JSON，但不会替代业务 schema 校验；JSON 内容不能直接按普通列建立索引，检索需选择提取列等方案。[MySQL 官方说明](https://dev.mysql.com/doc/refman/8.4/en/json.html)

### user_resume（必需）

| 字段 | 建议类型 | 语义 |
| --- | --- | --- |
| id | BIGINT PK | MyBatis-Plus ASSIGN_ID；HTTP 使用字符串避免 JS 精度问题 |
| user_id | BIGINT NOT NULL | 仅从 UserContextHolder 获取 |
| title | VARCHAR(120) | 列表标题，允许重复 |
| template_key | VARCHAR(64) | 代码注册的模板标识 |
| template_version | INT | 引用不可变模板版本 |
| schema_version | INT | 正文格式版本，区别于保存次数 |
| content | JSON | 基础资料、标准模块、自定义字段/模块 |
| layout | JSON | 模块排列、分栏、字体、颜色、边距等受限配置 |
| version | BIGINT | 并发控制，每次有效修改递增 |
| last_mutation_id | VARCHAR(64) NULL | 识别最近一次保存重试，不能替代完整幂等策略 |
| deleted_at | DATETIME(3) NULL | 若首期采用软删除；物理清理策略另定 |
| created_at / updated_at | DATETIME(3) | UTC，服务端生成 |

列表索引 `(user_id, deleted_at, updated_at, id)`；列表只取摘要列，禁止读取整份 content 或循环查照片/模板。详情按 id 与 user_id 限定。标题、版本、模板引用以列为唯一来源，避免 JSON 中另存一套而产生冲突。

### resume_template（若需要服务端模板目录，建议）

`id BIGINT PK, template_key VARCHAR(64), version INT, name VARCHAR(80), cover_path VARCHAR(512), default_content JSON, default_layout JSON, supported_schema_version INT, status VARCHAR(32), sort_order INT, created_at, updated_at`。

唯一键 `(template_key, version)`。受控代码/种子发布模板，不接受用户上传 HTML/JS 作为模板。前端与导出端的注册表必须支持相同版本；旧简历保留旧版本，不随模板更新静默变样。停用版本可禁止新建，但应继续支持既有简历。首期也可使用随代码发布的版本化清单，避免做无需求的模板后台。

### user_resume_revision（可选，历史恢复需求明确后增加）

`id, resume_id, user_id, version, schema_version, title, template_key, template_version, content JSON, layout JSON, reason, created_at`；唯一键 `(resume_id, version)`。快照必须包含模板和布局，才能恢复外观。不能每敲一个字写一条永久历史；按显式版本点或节流策略留存，并配置保留数量/期限。恢复是把快照写成新版本，不倒退 version。

### PDF 导出不建任务表（2026-10-05 更新）

按用户要求，不引入 resume_export_task 或其他导出任务表。浏览器导出与同步服务端导出都不必建立任务表，具体渲染方式另定。导出时固定读取一个已保存版本；不引入后台队列、任务轮询或任务历史。模板组件由 template_key + version 映射，不再保存独立 renderer_key。

## 4. 自定义字段与正文协议

三种需求要分清：

1. 基本信息新增“个人博客”“意向城市”：一个字段定义与值即可。
2. 新增“开源贡献”模块：可重复添加多个条目，保留标题、角色、日期、描述等常见结构。
3. 在模块条目中再新增“获奖级别”“仓库链接”：需要模块内字段定义及条目值映射，原参考项目未完整覆盖这一层。

建议标准模块保留有语义的结构，支持 customFields；自定义模块允许有限字段类型 TEXT/LINK/DATE/DATE_RANGE/RICH_TEXT，不扩展成通用低代码表单引擎。字段 ID 与名称分离，重命名不丢值；同名字段可以通过 ID 区分。删除定义同步删除所有条目对应值，隐藏则保留数据。字段类型变化必须做兼容检查，不自动丢弃不兼容值。

示例（日期等规则在 schema 中定义；以下为局部正文）：

```json
{
  "basic": {
    "name": "张三",
    "photoFileId": null,
    "customFields": [
      {"id":"field-blog","label":"个人博客","type":"LINK","value":"https://example.com","visible":true,"showLabel":true}
    ]
  },
  "sections": [
    {
      "id":"section-open-source",
      "type":"CUSTOM",
      "title":"开源贡献",
      "visible":true,
      "fieldDefinitions":[
        {"id":"field-repo","label":"仓库链接","type":"LINK","visible":true},
        {"id":"field-impact","label":"贡献说明","type":"RICH_TEXT","visible":true}
      ],
      "items":[
        {"id":"item-one","visible":true,"values":{"field-repo":"https://example.com/repo","field-impact":{"type":"doc","content":[{"type":"paragraph","content":[{"type":"text","text":"修复接口兼容问题"}]}]}}}
      ]
    }
  ]
}
```

数组顺序表达字段/条目顺序；布局若引用 section ID，必须保证引用有效且无重复。正文不允许任意 CSS/HTML/JS。富文本建议采用受限 Tiptap JSON AST，由前后端验证节点、属性、链接协议及大小；若用 HTML，则需成熟白名单清洗器，不能把参考项目的格式 normalize 当作安全清洗。

照片和证书保存 fileId，不存 Base64 和短期签名 URL。现有 IFileApi 主要针对头像，不能直接把简历图片当公开头像签名。需扩展独立用途与批量归属核验/私有读取契约；关联文件的处理应避免逐文件数据库查询。文件替换/简历复制可能共享对象，不能删除一份简历就直接删除所有附件。

## 5. 保存与并发

1. 创建时由后端校验模板版本并复制默认数据，用户资料仅作初始填充，后续不随个人资料变更覆盖简历。
2. 前端使用独立 Pinia 编辑状态，预览直接读取当前草稿。建议约 800ms 防抖保存（可调），另有手动保存；同一简历写请求串行，期间新输入合并到下一次。
3. 保存提交完整 content/layout、expectedVersion 和 mutationId。服务端校验结构、长度/数量/样式边界及文件归属。
4. MyBatis-Plus LambdaUpdateWrapper 按 id、user_id、未删除、expectedVersion 原子更新，并把 version 设置为 expectedVersion+1。更新条数为 0 时区分不存在与冲突；有 revision 时同事务写快照。无简单 XML SQL，无 N+1。
5. 沿用本项目 HTTP 200 + R.code 约定，冲突使用业务码 RESUME_VERSION_CONFLICT，不擅自改成另一套 HTTP 错误处理。
6. 网络失败不显示已保存。对超时且未知是否成功的请求，先比较服务端 version/mutationId 再重试；同一 mutationId 不重复推进版本，若已被后续写入覆盖则进入冲突处理。
7. 已确认保存只对应请求发出时的草稿代次；响应回来后若有新输入，仍保持待保存状态。多标签页冲突不能自动覆盖另一端，提供加载远端或另存本地副本。
8. 可用 IndexedDB 暂存未同步草稿，键包含 userId/resumeId/baseVersion；重新打开时对照版本恢复。退出登录清理本地敏感缓存，离线草稿保留策略需与用户体验一致。beforeunload 只能用于提醒，不能承诺退出时必定保存成功。
9. 导出前 flush 待保存内容并等待确认，再以确定的 version 导出；若版本已经变化返回冲突，不能悄悄导出另一份内容。

## 6. 接口草案

| 方法与路径 | 用途 |
| --- | --- |
| GET /resume/templates | 可创建模板与版本、封面、能力 |
| GET /resume/templates/{key}/versions/{version} | 解析已保存简历引用的模板，包括停用旧版本 |
| GET /resumes | 当前用户分页摘要列表 |
| POST /resumes | 从模板/空白创建；重复提交需幂等 |
| GET /resumes/{id} | 正文、布局、版本、按需批量获取的附件访问数据 |
| PUT /resumes/{id} | 完整文档保存，包含标题、模板与并发版本 |
| POST /resumes/{id}/duplicate | 按指定版本复制，重新分配简历 ID |
| DELETE /resumes/{id} | 带 expectedVersion 删除，避免与保存竞态 |
| POST /resumes/{id}/export | 如选择同步服务端导出，按确定版本直接返回 PDF；浏览器导出不需要此接口 |

所有接口从身份上下文获取用户，DTO 不接受可控制归属的 userId。列表模板信息批量处理；文件读取通过文件服务，不跨模块查 file_object。建议简历 CRUD 首期放现有 codekin_user 的 user.resume 业务相关类型包，遵循当前 controller/service/domain 约定；是否以后拆服务由实际负载和业务边界决定，不为了简历功能立即拆微服务。

## 7. PDF 导出决策

“前端能导出”指用户操作入口，并不必然要求 PDF 字节由浏览器 JS 生成。

| 方案 | 优点 | 限制 |
| --- | --- | --- |
| 浏览器打印并另存 PDF | 不增加渲染服务，复用 HTML/CSS | 用户需操作打印框，浏览器/字体/打印设置影响结果，不能静默保存 |
| Chromium 服务端打印（建议用于稳定一键下载） | 固定浏览器、字体、模板版本，直接生成 PDF | 增加浏览器运行环境、资源限额、超时、并发控制与维护成本 |
| canvas 图片 PDF | 接近截图，前端易下载 | 没有真实文字层，不适合作为投递 PDF 默认输出；长页也不是 A4 多页 |

Playwright 的 page.pdf 默认按 print CSS 生成 PDF，可设置纸张与背景打印；此能力不等于自动解决模板分页。[官方文档](https://playwright.dev/docs/api/class-page#page-pdf)

若选服务端渲染：复用前端纯 ResumeRenderer 与 PrintView，以固定受控页面加载指定快照；Java 控制鉴权和同步导出请求，可评估 Playwright Java 执行器，不能未经讨论擅自增加 Node 服务。渲染进程不加载用户传入的任意 URL，不携带用户 JWT；使用短期、限单次导出的凭据。图片/字体来自受控资源，不允许任意网络访问。成功必须等字体和图片真正加载，失败应显式报告，不能输出缺照片的“成功 PDF”。

版式要求：A4 210×297mm；统一字体资源与字号；页边距；标题尽量与后续内容同页；短条目避免跨页；长于一页的描述允许在段落/列表项处拆分，不能给整段无限 break-inside:avoid；双栏独立验证阅读顺序。预览缩放只用于显示，不改变导出排版。不要强行把任意长度内容缩成一页。首期可用流式预览加最终 PDF 预览；如果要求编辑预览逐页完全一致，应另做明确分页模型或直接展示同一渲染器生成的 PDF。

导出使用的临时快照及 PDF 都含个人数据，默认私有；同步返回 PDF 不要求落库，若保留文件则需鉴权读取、短期链接与过期清理；隐藏模块不进入导出或 AI 输入。文字可提取不代表所有招聘系统都能正确解析，尤其双栏应做顺序验证。

## 8. 实现顺序与验收

1. 确认 PDF 路径、自定义字段深度与首期模板，再冻结 schema 与接口，编写建表迁移草案。
2. 完成后端简历 CRUD、归属、版本冲突及模板目录；前端列表与创建接入真实接口。
3. 编辑器、标准模块、基础自定义字段、自定义模块、附件、自动保存与草稿恢复。
4. 同一渲染器完成模板切换、预览和打印布局；选定 PDF 方案后接入导出。
5. 集成验收：刷新重开、多标签冲突、保存期间继续输入、失败重试、复制和删除、附件私有访问、未知 schema、切模板不丢字段；列表查询次数不随条目增长。
6. PDF 样例覆盖中文/英文、缺省照片、超长链接、空模块、自定义字段、富文本列表、单页/多页/超长条目、单双栏。检查纸张尺寸、逐页图像、文字提取、超链接与无缺页/截断/多余空白页，不以“成功生成文件”作为验收。

待讨论的关键决策：服务端固定 Chromium 一键下载，还是首期浏览器打印；自定义字段是否延伸到标准经历/项目内部。数据库与渲染部署均尚未实施。
