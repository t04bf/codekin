# 头像直传与文件服务

日期：2026-10-04。

## 首期限制

以下是针对当前头像用途的产品及资源成本选择，并非通用行业标准。用户给出的 10 MiB 是示例，首期收紧为：

| 项目 | AVATAR 限制 |
| --- | --- |
| 原文件大小 | 1 字节至 5 MiB（5,242,880 字节） |
| 原文件格式 | JPEG/JPG、PNG、WebP；扩展名与 MIME 必须一致 |
| 最大宽/高 | 每边不超过 4096 像素 |
| 最大总像素 | 12,000,000，宽高同时符合也要满足这一项 |
| 正式头像 | 保持比例缩小到最长边 512 像素，不放大；生成静态 PNG |
| 元数据 | 重新编码，不保留源 EXIF、GPS、文本及动画数据 |
| 动画 | 不提供动画头像；动画 WebP 拒绝，PNG 按基础静态图重编码 |
| 单实例解码并发 | 默认 2，预算耗尽时返回可重试的业务错误；Nacos 可配置 1..8 |
| 签名申请频率 | 每用户每用途 10 分钟最多 10 次，Redis 原子计数 |
| 上传凭证 | 默认 5 分钟；绑定唯一临时 key、MIME、1..5 MiB 范围 |
| 上传确认 | 默认 15 分钟内完成；仅归属用户可确认 |
| 头像展示 | 正式对象短期 GET 签名，默认 1 小时；图片加载失败显示默认吉祥物 |

5 MiB 为头像保留足够的常见图片容量；总像素限制控制完整解码内存，512 像素输出减少展示传输量。高分辨率照片可能需先压缩或缩小。实际格式通过 ImageIO 校验，WebP 复用 TwelveMonkeys 解码器；检查尺寸后才完整解码，不能只依赖浏览器的扩展名或 MIME。此处“核验”是文件格式与尺寸校验，不包含违法或不适宜内容识别。

限制统一定义在共享 `model.file.enums.UploadType`。基础设施及有效期配置在 `deploy/nacos-config/codekin-file.yml`；前端从接口读限制，没有独立的大小白名单。

## 接口

网关为 `http://127.0.0.1:8080`。下列接口均使用已有 Bearer JWT 鉴权和统一 `R<T>` 响应，HTTP 状态约定保持为 200，依据业务 code 判断成功。S3 直传的响应遵循对象存储协议，不是 `R<T>`。

| 接口 | 用途 |
| --- | --- |
| `GET /api/files/upload-types` | 返回已开放用途及格式、大小和像素限制 |
| `POST /api/files/upload/signature` | 统一申请上传签名 |
| `POST /api/files/{fileId}/complete` | 验证真实图片并生成正式文件，重复确认 READY 文件返回同一结果 |
| `PUT /api/users/me/avatar` | 用户服务经 Dubbo 核验后设置头像 |
| `GET /api/users/me` | 返回本人资料和 `avatarUrl` |
| `GET /api/users/{userId}` | 返回公开资料和 `avatarUrl` |

申请签名入参：

```json
{"typeCode":"AVATAR","fileName":"avatar.png","size":123456,"contentType":"image/png"}
```

签名响应 data 包含 `fileId`（字符串）、`uploadUrl`、`method=POST`、`fields`、`expiresAt`、`confirmationExpiresAt`。上传使用 FormData：先逐项加入 fields，再在最后加入名为 `file` 的实际文件。浏览器自动生成 multipart boundary，不能手写带 boundary 的 Content-Type，也不附带应用 JWT 或 cookies。

确认响应 data 包含 `fileId`、`typeCode`、`size`、`contentType`；不返回内部存储路径或用户归属字段。设置头像入参：

```json
{"fileId":"确认成功的文件ID"}
```

## 调用流程

1. Element Plus 上传组件读取限制，选择图片并做初步校验及本地预览；点击弹窗确认后才执行上传。
2. 前端向文件服务申请签名；用户 ID 从网关签名后的请求上下文取得。
3. 浏览器直接向 SeaweedFS S3 POST 上传文件，文件正文不经过应用网关。
4. 前端请求文件确认。文件服务通过数据库条件更新取得处理权，限制大小读取、校验真实内容及像素，重新编码到 `files/avatar/{userId}/{fileId}.png`。
5. 前端携带 fileId 请求用户服务。用户服务通过 Dubbo 查询文件是否 READY、属于当前用户、用途为 AVATAR，先检查统一 `RpcResult` 成功码，再把正式 key 保存到本人资料。
6. 刷新本人资料，取得短期 avatarUrl；页头、个人主页、资料页共用 UserAvatar 展示，默认头像保留简单边框。

上传凭证只能写临时 `uploads/` key，不能修改正式 key。自定义头像接口不会接受客户端传入的任意 URL 或对象路径；默认头像选择接口只接受 Nacos 目录白名单内的对象路径。过期临时文件由定时任务批量清理，包括完成后被原凭证再次上传的临时对象；数据库操作使用批量查询与更新，没有按文件逐条查询。正式历史头像暂不自动删除，避免误删仍有引用的文件；本阶段没有实现历史文件引用回收。

POST Policy 的大小条件用于拒绝超限文件，但不能代替上线入口的 HTTP 请求体限制：接收请求本身仍消耗带宽和临时空间。当前 Compose 为本地开发单机部署，不额外引入生产反向代理。

## RPC 结果契约更新

文件 RPC 统一返回 `RpcResult<T>`（code、message、data），当前 Dubbo 契约版本为 `2.0`。业务异常由公共 `codekin_dubbo` 提供方过滤器转换，消费方集群过滤器处理最终调用失败。查询失败不直接返回 null，头像调用方检查结果码；头像访问失败仍回退到默认头像。文件和用户服务须使用同一套新契约重启，详细约定见 [RPC 统一返回说明](4.%20RPC统一返回与异常处理-2026-10-04.md)。
